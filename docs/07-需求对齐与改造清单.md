# 07 需求对齐与改造清单（打磨版）

> 本文对应《二手书打磨.txt》提出的「三端 + 四个第三方接口 + 11 条交易细节」，逐条说明系统当前的落地方式、代码位置与仍存在的差距。答辩时可直接用第 1、2 节的两张表讲「需求怎么变成设计」。

## 1. 一句话结论

| 维度 | 改造前（第一版） | 改造后（本版） |
| --- | --- | --- |
| 交易场地 | 校园自提点 + 店员核销 | **买卖双方线下约见**，时间地点在订单里协商确认 |
| 核销方式 | 店员输入动态码 | **卖家输入 6 位核销码 + 上传签到照**，买家出示、15 分钟有效 |
| 订单状态 | 7 态（支付/冻结/待核销/已核销/已结算/退款/关闭） | **三态主干**：`PENDING_PAY → WAIT_VERIFY → COMPLETED`，退款/仲裁为旁支 |
| 登录 | 账号密码 + 微信 code | **全站短信验证码登录**（默认 mock 回传验证码；已接 Spug 推送助手真实短信通道，见 3.1） |
| 交易门槛 | 无 | **实名 + 学生双认证**后才能下单/发布 |
| 纠纷 | 无（只有工单） | **退款申请 → 卖家同意/拒绝 → 平台介入判定**完整链路 |
| 供给端 | 只有个体卖家 | **个体端 + 商户端 + 平台端**三端 |

## 3. 四个第三方接口的接入方式

| 能力 | 接口 | 开发期（当前） | 上线切换 |
| --- | --- | --- | --- |
| 扫描 ISBN 获取书籍信息 | `GET /v1/isbn/{isbn}` | 查本地 `sys_textbook`（ISBN-13 精确匹配），未命中返回 `found=false` 引导手填 | 接开放图书 API 后，`IsbnService` 内改为先远程后本地 |
| 短信验证码 | `POST /v1/auth/sms-code` | 默认 `app.sms-provider=mock`：验证码写 `sys_sms_code` 并随响应回传 `devCode`；同号 60 秒频控（dev 调为 3 秒）。**已接入真实通道 Spug 推送助手**：`app.sms-provider=spug` + `app.spug-template-code` → `POST https://push.spug.cc/sms/<模板编码> {"to","code"}` | 换阿里云 SMS 只需新增一个 `SmsProvider` 实现，业务零改动 |
| 身份证核验 | `POST /v1/verify/id-card` | **已接阿里云云市场「身份证二要素」**（`app.identity-provider=aliyun`，AppCode 鉴权，免费试用 10 次 / 到期 2026-12-29）；默认 `mock` 只做 GB11643 本地校验 | 换官方实人认证（EKYC）需企业资质；AppCode 过期后改配置即可 |
| 人脸识别 | `POST /v1/verify/face` | mock 直接通过 | 同上，接活体检测 SDK |

> 为什么要做 `provider 开关`：本机没有任何第三方账号与资质，但毕设答辩必须能完整演示。把「能力」和「供应商」解耦后，演示走 mock、上线只改配置，代码零改动。

### 3.1 短信通道：Spug 推送助手（已接入，真机实测已发通）

- 代码结构：`server/src/main/java/com/textbook/loop/sms/` —— `SmsProvider`（接口）、`MockSmsProvider`（开发）、
  `SpugSmsProvider`（真实）、`SmsConfig`（按 `app.sms-provider` 装配；填了 `spug` 但漏模板编码会**回退 mock 并告警**）。
- 凭证：Spug 控制台 → **短信验证码** → 选官方模板 → 模板详情里复制完整调用 URL
  `https://push.spug.cc/sms/<TEMPLATE_CODE>`，`<TEMPLATE_CODE>` 就是凭证（只放服务端，绝不进前端/小程序包）。
- 启用真实发送：

  ```powershell
  # 方式一：叠加 spug profile（模板编码放本机私有文件 application-spug-local.yml，已被 .gitignore 忽略）
  #   server/src/main/resources/application-spug-local.yml
  #   app:
  #     spug-template-code: <模板编码>
  java -jar server\target\textbook-loop-server-0.1.0.jar --spring.profiles.active=dev,spug

  # 方式二：环境变量（服务器/容器部署用这个，镜像里不落盘）
  $env:APP_SMS_PROVIDER="spug"; $env:APP_SPUG_TEMPLATE_CODE="<模板编码>"
  ```

  > 模板编码等同于账号凭证，**不要提交进仓库**。仓库里的 `application-spug.yml` 只有占位符
  > `${APP_SPUG_TEMPLATE_CODE:}`，漏配时 `SmsConfig` 回退 mock 并打 WARN。

- 启停脚本：`tools\start-backend.ps1` —— 默认 `-Sms mock`，`-Sms spug` 走真实短信，`-Reset` 先清库；
  它会停掉 8088 上的旧进程、等 `/v1/health` 就绪、打印实际 profile 与 PID。
  （`tools\reset-dev.ps1` 只负责「清库重启」，短信通道等同 mock。）
- 真实模式行为：`/v1/auth/sms-code` 不再返回 `devCode`，失败时返回 `40000 短信发送失败：<Spug 的 msg>`；
  日志里只打印脱敏手机号与 `request_id`（可用 Spug「发送记录」或查询 API 追踪投递）。
- **前置条件（实测依次踩到，按顺序解决即可）**：
  1. Spug 账户未完成**实名认证**时返回
     `{"code":403,"msg":"账户未通过实名认证，请前往个人设置/实名认证完成认证后再试"}`；
  2. 实名通过后仍可能返回
     `{"code":403,"msg":"请求IP: <你的出口IP> 不在IP白名单内，请添加此IP至短信配置/IP白名单后再试"}` ——
     到控制台「短信验证码 → IP 白名单」把**服务器出口 IP** 加进去（本机调试加宽带出口 IP，
     部署到云服务器后要再加一次 ECS 的公网出口 IP，否则线上登录会被同样拦住）；
  3. 短信是付费通道，确认账户有余额/额度。
- 实测结果（2026-11-27）：`POST /v1/auth/sms-code {"phone":"18077634***"}` 返回
  `{"code":0,"data":{"provider":"spug","devCode":null,"sent":true}}`，手机收到 6 位验证码；
  再用该码 `POST /v1/auth/sms-login` 返回 token（未注册手机号自动建号，昵称「同学****」），
  即「发码 → 收码 → 验证码登录」全链路已跑通。
- 冒烟脚本仍用 mock（依赖 `devCode` 自动登录），真实短信模式请手工点一次登录验证。
### 3.2 身份证核验：阿里云云市场「二要素」（已接入，试用 10 次 / 到期 2026-12-29）

- 选型理由：官方「实人认证 EKYC」多要求**企业实名**，个人毕设拿不到资质；云市场第三方「身份证二要素」对个人实名账号开放，有免费试用，一次调用即可判定「姓名 + 身份证号是否一致」，足够支撑论文里的第三方接口章节。
- 代码结构：`server/src/main/java/com/textbook/loop/realname/` —— `RealNameProvider`（接口，`CheckResult check(name, idNo)`）、
  `MockRealNameProvider`（只做 GB11643 校验位 + 出生日期，离线演示）、`AliyunMarketRealNameProvider`（真实调用）、
  `RealNameConfig`（按 `app.identity-provider` 装配；配了 aliyun 却没 AppCode 会**回退 mock 并告警**）；
  本地校验工具 `server/src/main/java/com/textbook/loop/service/IdCardUtil.java`。
- 调用契约（实测）：`POST https://verifytwo.market.alicloudapi.com/identity/verify_id_name?name=<姓名>&id_number=<18位>`
  + 请求头 `Authorization: APPCODE <appcode>`；返回 `{"result_code":"0000","result":{"checkresult":1|2,"message":"..."},"charge":1}`，
  **`result_code=0000` 且 `checkresult=1` 才判定一致**；`charge=1` 表示本次消耗 1 次额度。
- 启用方式：`app.identity-provider=aliyun` + `app.aliyun-market-appcode=<AppCode>`；AppCode 只放
  `server/src/main/resources/application-identity-local.yml`（已 gitignore）或环境变量 `ALIYUN_MARKET_APPCODE`。
- 实测结果（2026-11-28）：用合成号码 `110101199001011237` + 姓名「张三」调 `POST /v1/verify/id-card` →
  返回 `{"code":40900,"message":"实名认证未通过：身份证号和姓名不一致"}`，证明链路真实打通（拒绝路径）；
  姓名与号码一致时会置 `id_verified=1` 并写 `sys_verify_record`（通过路径同理，只是需要真实信息）。
- 降级方案（额度耗尽或换不了真实凭证时）：正反面照片落盘 → GB11643 本地校验 → 平台端人工审核（admin 已可审）。
- ⚠️ 凭证轮换提醒：模板编码曾短暂出现在一次提交里（已 `--amend` + `--force-with-lease` 清除），
  稳妥做法是在 Spug 控制台删除该模板、重新生成一个编码再填进上面的私有文件或环境变量。

## 6. 仍存在的差距（诚实清单）

1. **第三方服务接入状态**：短信**已接真实通道 Spug 推送助手**（app.sms-provider=spug）；**身份证核验已接阿里云云市场二要素**（app.identity-provider=aliyun，AppCode 试用 10 次）；人脸识别仍是 mock；ISBN 只查本地库；微信支付未接。答辩时说明「能力与供应商解耦，换供应商只改配置」，并现场演示真实短信 + 实名核验。
2. **存储是本地磁盘**：`POST /v1/files/upload` 已实现图片/视频上传，文件落在 `uploads/` 并按月分目录；单机可用，多实例或上云需替换为 OSS/S3（接口不变）。
3. **爽约扣分未自动化测试**：需要「约定时间 + 30 分钟」才允许上报，脚本没有等待；逻辑已实现，可在手工演示中把约见时间设为过去时间验证。
4. **运营端推广二维码未生成图片**：后端返回推广码与推广链接（`/#/register?promo=CODE`），前端复制链接后在浏览器生成二维码；未引入二维码图形库。
5. **提成只落明细，未做打款**：`biz_commission` 记录待结算/已结算状态，实际打款仍线下完成。
6. **小程序端未跟进新版交易流程**：小程序仍按「店员核销」旧流程实现，定位为「参考实现/非主交付」，主线在响应式 Web（`web/`）。
7. **平台介入只判买卖责任，无申诉与举证时限**：`biz_refund` 有 `platform_verdict`，但没有二次申诉表；属于可接受的范围控制。
8. **商户结算未做分账**：`biz_settlement` 仍按单笔记录平台佣金，离线打款，不接支付渠道分账。

## 7. 演示脚本建议（5 分钟）

1. 游客打开 Web 首页 → 搜索「高等数学」→ 进详情看价格指数（无需登录）。
2. 用 `13800000002` 短信登录 → 发布一本教材：扫码/手填 ISBN 自动带出书名 → 传 7 张照片。
3. 换 `13800000003` 登录 → 找到该商品下单支付（或反向：买家买卖家的书）。
4. 买家订单页看 **6 位核销码倒计时**；卖家在订单页**输入核销码 + 上传签到照**完成交易。
5. 买家申请退款 → 卖家拒绝 → 买家申请平台介入 → 管理员（`13800000001`）在后台判定「卖家责任」→ 订单自动退款。
6. 后台看板看 GMV、订单漏斗、品相分布；商户端批量上下架。
