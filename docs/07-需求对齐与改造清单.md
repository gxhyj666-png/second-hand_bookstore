# 07 需求对齐与改造清单（打磨版）

> 本文对应《二手书打磨.txt》提出的「三端 + 四个第三方接口 + 11 条交易细节」，逐条说明系统当前的落地方式、代码位置与仍存在的差距。答辩时可直接用第 1、2 节的两张表讲「需求怎么变成设计」。

## 1. 一句话结论

| 维度 | 改造前（第一版） | 改造后（本版） |
| --- | --- | --- |
| 交易场地 | 校园自提点 + 店员核销 | **买卖双方线下约见**，时间地点在订单里协商确认 |
| 核销方式 | 店员输入动态码 | **卖家输入 6 位核销码 + 上传签到照**，买家出示、15 分钟有效 |
| 订单状态 | 7 态（支付/冻结/待核销/已核销/已结算/退款/关闭） | **三态主干**：`PENDING_PAY → WAIT_VERIFY → COMPLETED`，退款/仲裁为旁支 |
| 登录 | 账号密码 + 微信 code | **全站短信验证码登录**（默认 mock 回传验证码；已接 Spug 推送助手真实短信通道，见 3.1） |
| 交易门槛 | 无 | **实名 + 学生双认证**后才能下单/发布 |
| 纠纷 | 无（只有工单） | **退款申请 → 卖家同意/拒绝 → 平台介入判定**完整链路 |
| 供给端 | 只有个体卖家 | **个体端 + 商户端 + 平台端**三端 |

## 2. 11 条交易细节逐条对照

| # | 需求 | 实现位置 | 状态 |
| --- | --- | --- | --- |
| 1 | 买卖双方在对话界面发起交易地点与时间、买家确认 | `biz_meet` 表；`OrderService.proposeMeet/confirmMeet`；`POST /v1/orders/{orderNo}/meets`、`POST /v1/orders/meets/{meetId}/confirm` | 已实现（订单页 + 私信卡片） |
| 2 | 货物不符可申请退款退货，退货同样约时间地点 | `biz_refund`；`OrderService.applyRefund`；退货约见用同一 `biz_meet`（`meet_type=RETURN`） | 已实现 |
| 3 | 协商不成申请平台介入；无问题终止退货、有问题强制退款 | `OrderService.requestArbitration / arbitrate / judge`；`biz_refund.platform_verdict`（`SELLER_FAULT` / `PLATFORM_OK`） | 已实现（管理员判定） |
| 4 | 扫码录入后拍照：封面、封底、出版日期、随机四页正文 | `biz_listing_photo`；`POST /v1/listings/{id}/photos`（`COVER/BACK/PUBLISH_DATE/CONTENT1..4`） | 已实现（7 个必传位） |
| 5 | 线下交易卖家上传签到照；超时 30 分钟未到可上报，扣 5 信誉分 | `OrderService.verify(..., signPhotoUrl)`、`reportNoShow`；`biz_no_show(credit_delta=-5)` | 已实现（脚本未自动覆盖超时分支，因需等待 30 分钟） |
| 6 | 订单仅三态，待支付超时自动取消 | `@Scheduled closeExpiredOrders()`（`app.order-expire-minutes=15`） | 已实现 |
| 7 | 支付后生成 6 位核销码、15 分钟有效、线下由**卖家**输入 | `OrderService.verifyCode/verify`；`app.verify-code-ttl-minutes=15` | 已实现（过期可刷新换码） |
| 8 | 完整流程闭环（下单→约见→核销→退货→再次约见→退款→介入） | `OrderService` + `biz_meet` + `biz_refund` | 已实现，`tools/e2e-trade.ps1` 覆盖两条分支 |
| 9 | 所有用户登录走短信验证码 | `SmsService`；`POST /v1/auth/sms-code`、`/v1/auth/sms-login` | 已实现（mock；账号密码登录保留为后台/兼容） |
| 10 | 游客可浏览，交易/私信需登录，交易还要实名+学生认证 | `AuthInterceptor` 只解析不拦截；`IdentityService.requireTradePermission` | 已实现 |
| 11 | 实名认证传身份证正反面 + 三方核验；学生认证传学生证封面 + 信息页 | `sys_verify_record`；`POST /v1/verify/id-card|student|face`；`IdentityService` | 已实现（mock 通过，切真实服务见第 4 节） |

## 3. 四个第三方接口的接入方式

| 能力 | 接口 | 开发期（当前） | 上线切换 |
| --- | --- | --- | --- |
| 扫描 ISBN 获取书籍信息 | `GET /v1/isbn/{isbn}` | 查本地 `sys_textbook`（ISBN-13 精确匹配），未命中返回 `found=false` 引导手填 | 接开放图书 API 后，`IsbnService` 内改为先远程后本地 |
| 短信验证码 | `POST /v1/auth/sms-code` | 默认 `app.sms-provider=mock`：验证码写 `sys_sms_code` 并随响应回传 `devCode`；同号 60 秒频控（dev 调为 3 秒）。**已接入真实通道 Spug 推送助手**：`app.sms-provider=spug` + `app.spug-template-code` → `POST https://push.spug.cc/sms/<模板编码> {"to","code"}` | 换阿里云 SMS 只需新增一个 `SmsProvider` 实现，业务零改动 |
| 身份证核验 | `POST /v1/verify/id-card` | `app.mock-identity=true` 直接置 `id_verified=1` | 接实人认证/OCR 服务，写 `sys_verify_record` 留痕 |
| 人脸识别 | `POST /v1/verify/face` | mock 直接通过 | 同上，接活体检测 SDK |

> 为什么要做 `provider 开关`：本机没有任何第三方账号与资质，但毕设答辩必须能完整演示。把「能力」和「供应商」解耦后，演示走 mock、上线只改配置，代码零改动。

### 3.1 短信通道：Spug 推送助手（已接入，可直接真实发送）

- 代码结构：`server/src/main/java/com/textbook/loop/sms/` —— `SmsProvider`（接口）、`MockSmsProvider`（开发）、
  `SpugSmsProvider`（真实）、`SmsConfig`（按 `app.sms-provider` 装配；填了 `spug` 但漏模板编码会**回退 mock 并告警**）。
- 凭证：Spug 控制台 → **短信验证码** → 选官方模板 → 模板详情里复制完整调用 URL
  `https://push.spug.cc/sms/<TEMPLATE_CODE>`，`<TEMPLATE_CODE>` 就是凭证（只放服务端，绝不进前端/小程序包）。
- 启用真实发送：

  ```powershell
  # 方式一：叠加 spug profile（模板编码已写在 application-spug.yml）
  java -jar server\target\textbook-loop-server-0.1.0.jar --spring.profiles.active=dev,spug

  # 方式二：环境变量
  $env:APP_SMS_PROVIDER="spug"; $env:APP_SPUG_TEMPLATE_CODE="<模板编码>"
  ```

- 真实模式行为：`/v1/auth/sms-code` 不再返回 `devCode`，失败时返回 `40000 短信发送失败：<Spug 的 msg>`；
  日志里只打印脱敏手机号与 `request_id`（可用 Spug「发送记录」或查询 API 追踪投递）。
- **前置条件（实测踩到）**：Spug 账户未完成**实名认证**时接口返回
  `{"code":403,"msg":"账户未通过实名认证，请前往个人设置/实名认证完成认证后再试"}`；
  短信为付费通道，还需要账户余额。这两步在 Spug 侧完成，代码不用改。
- 冒烟脚本仍用 mock（依赖 `devCode` 自动登录），真实短信模式请手工点一次登录验证。

`biz_orders` 增列：`verify_expire_at`、`meet_place`、`meet_time`、`sign_photo_url`、`sign_at`、`merchant_id`、`completed_at`；`verify_code` 放宽到 16 位。

- 认证：`/v1/auth/sms-code`、`/v1/auth/sms-login`、`/v1/verify/id-card`、`/v1/verify/student`、`/v1/verify/face`、`/v1/verify/status`

- 商品：`POST/GET /v1/listings/{id}/photos`；`GET /v1/isbn/{isbn}`
- 私信：`POST /v1/conversations`、`GET /v1/conversations`、`GET /v1/conversations/{id}/messages`、`POST /v1/conversations/{id}/messages`

## 6. 仍存在的差距（诚实清单）

1. **第三方服务接入状态**：短信**已接真实通道 Spug 推送助手**（app.sms-provider=spug，需在 Spug 完成实名认证与充值）；身份证核验、人脸识别仍是 mock；ISBN 只查本地库。答辩时说明「能力与供应商解耦，换供应商只改配置」并现场演示一次真实短信。
2. **图片只存 URL 字符串**：没有对象存储与上传接口，前端目前提交的是本地预览地址（如 `demo/cover.jpg`）。上线需接 OSS + 上传签名。
3. **爽约扣分未自动化测试**：需要「约定时间 + 30 分钟」才允许上报，脚本没有等待；逻辑已实现，可在手工演示中把约见时间设为过去时间验证。
4. **小程序端未跟进新版交易流程**：小程序仍按「店员核销」旧流程实现，定位为「参考实现/非主交付」，主线在响应式 Web（`web/`）。
5. **平台介入只判买卖责任，无申诉与举证时限**：`biz_refund` 有 `platform_verdict`，但没有二次申诉表；属于可接受的范围控制。
6. **商户结算未做分账**：`biz_settlement` 仍按单笔记录平台佣金，离线打款，不接支付渠道分账。

## 7. 演示脚本建议（5 分钟）

1. 游客打开 Web 首页 → 搜索「高等数学」→ 进详情看价格指数（无需登录）。
2. 用 `13800000002` 短信登录 → 发布一本教材：扫码/手填 ISBN 自动带出书名 → 传 7 张照片。
3. 换 `13800000003` 登录 → 找到该商品下单支付（或反向：买家买卖家的书）。
4. 买家订单页看 **6 位核销码倒计时**；卖家在订单页**输入核销码 + 上传签到照**完成交易。
5. 买家申请退款 → 卖家拒绝 → 买家申请平台介入 → 管理员（`13800000001`）在后台判定「卖家责任」→ 订单自动退款。
6. 后台看板看 GMV、订单漏斗、品相分布；商户端批量上下架。
