### 5.2 执行方式

- JMeter 5.6：线程组 + HTTP Request（Header `Authorization: Bearer ${token}`）+ 聚合报告 + 断言（响应 `"code":0`）。
- 计划文件与命令行见 `tools/perf/README.md`；没有 JMeter 时用 `tools/perf/concurrent-order.ps1`（`ForEach-Object -Parallel`）做抢单验证。

> 数据说明：读接口 1000 请求 0 失败，说明在本数据规模（38 表 / 12 件在售）下读路径不是瓶颈；写接口的 20 并发已足以证明条件更新 + 幂等表的防超卖逻辑成立（更多并发只会让失败数上升，不会多出成功单）。
> 局限：本机是 H2 文件库 + JVM 512 MB 堆，ECS 上（MySQL 8 + 2C4G）应用 `tools/perf/load-list.ps1` 重跑一遍再回填本表，论文里注明环境差异。

### 5.4 结论（写论文时的论证方向）

1. `POST /v1/orders` 用 `UPDATE … WHERE status='ON_SALE'` 条件更新，100 并发抢同一本书**只有 1 条 update 影响行数为 1**，其余抛 40900 → 从原理上不存在超卖。
2. 列表/详情/推荐三类读接口在 38 表规模、20 并发下 TPS 均超过 1000、P95 < 70 ms，瓶颈会先出现在 JVM 堆（`-Xmx512m`）而不是数据库。
3. 关键词检索走 `LIKE '%…%'` **用不到索引**，是真实瓶颈；论文中可对比「前缀匹配 + 索引」与「全文检索（MySQL FULLTEXT / Elasticsearch）」的取舍，作为"进一步工作"。
## 6. 测试结论

- **功能覆盖**：主链路 17 项 + 分支 21 项 = **38 条自动化断言全部通过**，覆盖「发布 → 下单 → 支付 → 取码 → 约见 → 核销 → 评价 → 信用」「退款两条分支（协商同意 / 拒绝后平台仲裁）」「私信」「商户入驻 → 审核 → 批量上下架 → 统计」「ISBN 双通道」。
- **接口覆盖**：133 个接口中，被自动化脚本直接命中的约 48 个（主链路 + 分支 + 角色准入）；其余为管理端 CRUD 与运营端接口，由平台端页面手工验证。
- **缺陷记录**：测试过程中发现并修复的真实缺陷 8 个（评价状态写死旧枚举、GMV 统计漏算、核销码对未支付订单也发放、脚本"假绿"、卖家选品条件错误、短信频控不可配置、e2e 不可重复执行、ISBN 上游 400 被当异常）。详见 `docs/05-开发会话与交付记录.md`。
- **残留风险**：①人脸识别、微信支付仍为 mock；②性能结论需在本机跑完 TC-P01–P04 后回填具体数字；③问卷（287 份）优先在真实用户中回收，不在本文范围内。
