## 一、题目

基于 Spring Boot 3 与微信小程序的校园教材循环平台的设计与实现

## 二、设计背景与意义

### 2.1 设计背景

高校教材是典型的强时效、弱磨损商品。一门课的教材通常只被重点翻阅若干章节，纸张损耗远低于其信息价值，课程结束后对原持有者不再产生效用，而下届学生仍有刚性需求。理论上教材应在年级间循环，实际却大量沉淀在宿舍书架与毕业季的废纸回收车上。

直接原因是版本制度。同济大学数学系编《高等数学》第六版与第七版在章节编排、习题编号上均有差异，教师按某一版次布置作业，持另一版次的学生无法跟上进度。出版社修订、规划教材更新、更换授课教师都会触发版本更替，旧版在课堂场景中的价值迅速归零，在二手市场却仍以"高等数学上册"的名义流通。书名相同、版次不同，是教材循环中最易出错的一环。

第二个原因是信息分散：校园流转依赖班级群消息与宿舍楼下的张贴，群聊信息数小时即被淹没，没有检索与价格参照，交易靠熟人关系与口头约定，出现版本不符时双方都无凭证。第三个原因是信任与履约机制缺失：单笔金额多为十元至数十元，先付款则买方担心收不到书，先交书则卖方担心收不到钱，线下自提又缺少统一的交付确认手段。从需求侧看，全国普通高校本专科在校生规模稳定在三千七百万人以上，教材支出是每学期无法回避的开销。

### 2.2 设计意义

理论意义在于把"课程—教材—版次"的对应关系抽象为可维护的数据模型，并据此讨论二手交易中标的物同一性的判定。二手交易的核心风险不是支付通道，而是买方以为买到的与卖方实际交付的是否为同一物；教材场景把这一问题放大到极致，因为同书名的不同版次外观高度相似。用课程锚点、ISBN 主数据与教师学期三重校验把自然语言描述转换为结构化约束，可为同类标准化商品的二手流转提供可复用的建模思路。

实践意义有四：降低教材支出，一本定价四十五元的教材若循环两次，单次使用成本降至十五元以下；把分散的社群信息沉淀为可检索资产，支持按课程、版次、品相、距离筛选；为学校提供教材使用与闲置数据；完成一次环节完整的工程训练，覆盖认证鉴权、主数据管理、检索推荐、状态机、资金一致性、线下核销与数据看板。

## 三、国内外研究现状

国内二手书流通可分三类。一是综合平台，以闲鱼、转转为主，担保体系成熟，闲鱼"货款冻结—确认收货—打款卖家"的流程已是国内 C2C 的事实标准；但其类目面向全品类，教材只是"图书"下的长尾，缺少课程、版次、教师维度。二是垂直书商，多抓鱼以 C2B2C 回收—翻新—再售并建立品相分级，其品相与定价的关系有参考价值，但依赖中心仓与物流，单本物流成本常超过教材残值；孔夫子旧书网长于稀缺旧书与版本目录，教材时效性并非重心。三是校园自建平台与实体驿站，多为"发布—浏览—联系"三步，普遍缺少版本校验、担保交易与信用积累，常因供给不足与纠纷无法处理而停摆。

国外教材市场的特征是高定价加租赁制。Chegg 以租赁为核心，学生按学期付租金、到期寄回；CampusBooks、TextbookRush 以 ISBN 为检索入口提供多形态比价；Barnes & Noble College 等校园书店与学校绑定承担线下履约。其关键基础设施是 ISBN 标准与出版元数据服务，版本、版次、装帧被完整结构化，检索与比价得以自动化。学术上，Sarwar 等提出的 ItemCF 奠定了同类推荐的基础；近年图神经网络推荐在稀疏场景有改进，但工程复杂度较高。

综上，国外以 ISBN 驱动的租赁与回购解决了版本可识别，但依赖成熟元数据与物流；国内以流量平台与社群解决了信息发布，却未解决版本对齐与履约凭证。二者的空白是：在一所学校内部，如何以课程为锚点把"教师今年指定的到底是哪一本"变成系统可判定的结构化事实，并在此基础上完成带担保、可核销、可追溯的交易闭环。

## 四、主要内容与工作量

研究内容包括六项：需求分析与用例建模，梳理买家、卖家、团长、店员、管理员五类参与者的用例；数据库设计，围绕"学校—课程—教材—商品—订单—履约—信用"主线设计二十四张表，完成三级建模及索引、枚举、审计字段规范；后端实现，基于 Spring Boot 3 构建分层单体，实现八组能力并提供统一响应结构的 REST 接口；小程序实现，用原生框架完成推荐、搜索、详情、发布、订单、核销码、接龙与个人中心；管理后台实现，用 Vue 3 与 Element Plus 完成审核、主数据维护、订单结算、工单与看板；测试与部署，重点覆盖状态流转、幂等下单、并发核销与超时关单。

工作量方面，数据表二十四张、字段二百六十三个；后端约九十个 Java 类型；对外接口六十余个，统一以 `/v1` 为版本前缀；小程序约二十五个页面与组件，管理后台约十八个视图；测试用例约八十条；开发周期十二周，其中编码约六周。

## 五、系统功能模块设计

系统采用前后端分离的单体架构：小程序与管理后台通过 HTTPS 调用后端接口，JWT 承载登录态，MySQL 为唯一事实来源，缓存与定时任务作为性能与时效补充。角色共四类：学生（STUDENT）、团长（LEADER）、店员（CLERK）、管理员（ADMIN）。卖家不是独立角色，而是任一发布过商品的用户在自有商品上的相对身份，故 `sys_user.role` 只取上述四值，卖家权限由资源归属校验实现。

### 5.1 模块一 用户与认证

**功能描述**　负责身份的建立、校验与撤销，包括微信一键登录（开发态用 code 模拟 openid）、手机号注册与登录、JWT 令牌鉴权（有效期 7 天）、学号实名认证与管理员审核、四类角色的接口与数据权限控制、账号冻结与解冻。

**业务流程**

（1）`wx.login` 取 code 请求 `POST /v1/auth/wechat`：开发环境把 code 直接当作 openid（正式环境在该处替换为 `jscode2session` 调用），session_key 不落库。

（2）按 openid 查 `sys_user`：存在且 `status` 为 NORMAL 则签发令牌，否则创建 `role=STUDENT`、`verify_state=UNVERIFIED` 的记录。

（3）`POST /v1/auth/verify-student` 提交实名信息置 PENDING；管理员调 `POST /v1/admin/users/{id}/verify` 置 VERIFIED 或 REJECTED，操作写 `sys_admin_log`。

（4）后续请求携带 Bearer 令牌，拦截器验签并写入 ThreadLocal；冻结接口置 FROZEN 后，后续请求在拦截器读取用户状态时直接拒绝。

**技术要点**　鉴权用 jjwt 自实现而非 Spring Security：角色只有四种、数据规则只有资源归属一种，引入完整安全框架的配置与调试成本大于收益，只取 BCrypt 做密码哈希。令牌只有一枚、有效期 7 天（`app.jwt-ttl-hours=168`），过期由客户端重新登录；角色校验由拦截器加 `UserContext.requireAdmin()` 与 Service 层资源归属校验完成，未引入注解式 AOP。JWT 签发后无法单方撤销，故冻结采用"每请求读一次用户状态"，冻结后下一次请求即被拒绝。

**关键表与接口**　表：`sys_user`、`user_auth`、`sys_school`、`sys_admin_log`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/auth/register` | 手机号注册 |
| POST | `/v1/auth/login` | 账号密码登录 |
| POST | `/v1/auth/wechat` | 微信 code 换登录态（开发态模拟） |
| GET | `/v1/auth/me` | 当前登录信息 |
| PUT | `/v1/auth/profile` | 修改资料 |
| POST | `/v1/auth/verify-student` | 提交实名认证 |
| POST | `/v1/admin/users/{id}/verify` | 管理员审核实名 |
| POST | `/v1/admin/users/{id}/freeze` | 冻结账号 |

### 5.2 模块二 课程—教材知识库

**功能描述**　本模块是数据地基，解决"这门课今年用哪本书"。课程库维护课程代码、名称、开课学院、学期与教师；教材主数据以 ISBN 为唯一标识，记录书名、作者、出版社、版次、出版年与定价；二者为多对多映射，映射携带必修（REQUIRED）或参考（REFERENCE）标识、教师与学期；同书名不同版次必须是两条独立记录；误录重复时提供教材合并。

**业务流程**

（1）管理员录入课程，课程代码作为教务系统对接的外部键。

（2）录入教材：ISBN-13 先查 `sys_textbook.isbn13`，命中即复用，未命中调第三方元数据接口预填；版次必填，从数据层杜绝只有书名的记录。

（3）建立映射：选课程与教材，指定绑定类型、教师与学期写入 `sys_course_textbook`，组合由唯一键约束。

（4）冲突检测：同课程同学期已有另一条 REQUIRED 绑定且教师相同时提示管理员确认新旧版共存还是录入错误，未确认则阻断。

（5）学生进入课程详情看到指定教材与参考教材，均以"书名（版次）"展示，点击跳转该教材在售列表；卖家发布时必须从该库选择，手中是旧版须显式切换到参考教材，不能自由输入书名。

**技术要点**　版本歧义按结构化优先、展示强制处理：教材同一性由 ISBN 决定，故以 `isbn13` 建唯一键，一书一版一条记录；书名与版次分列而非拼进书名，检索才能按版次过滤、统计才能按版次聚合，也避免"第七版"与"第7版"重复。`sys_course_textbook` 是带属性的映射实体，因为同一教材在不同课程与学期的地位不同。

**关键表与接口**　表：`sys_course`、`sys_textbook`、`sys_course_textbook`、`biz_listing`（合并时迁移关联）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/courses` | 课程列表 |
| GET | `/v1/courses/{id}/textbooks` | 课程绑定教材（含必修/参考） |
| GET | `/v1/textbooks` | 教材检索，支持 keyword、isbn |
| POST | `/v1/admin/textbooks` | 新增教材 |
| POST | `/v1/admin/course-textbooks` | 建立映射 |
| GET | `/v1/admin/course-textbooks/conflicts` | 版本冲突列表 |

### 5.3 模块三 商品发布与品相管理

**功能描述**　把一本具体的旧书转化为可交易商品。发布时通过 ISBN 扫码或教材库搜索定位，自动带出书名、版次与原定价；品相分 NEW、LIKE_NEW、GOOD、FAIR、POOR 五档；图片一至九张，首图为封面；提供同教材历史成交价参考；支持上架、下架与审核驳回，订单锁定期间禁止编辑与下架。

**业务流程**

（1）卖家扫码，`wx.scanCode` 得到 ISBN-13，请求 `GET /v1/textbooks?isbn=xxx` 带出教材信息，未命中则引导提交新增教材申请。

（2）填写售价、品相、描述与自提点，页面实时展示定价参考：同教材近九十天已结算订单的最低价、最高价、均价与样本数，样本不足三条时降级为在售价区间并标注。

（3）图片经 `POST /v1/uploads/images` 直传，服务端算 MD5、压缩至长边一千二百像素并写入对象存储，返回地址与 MD5。

（4）提交 `POST /v1/listings`，校验教材存在、价格在原定价一成至原价之间、品相合法、图片一至九张，通过后写入，`status` 为 ON_SALE，`published_at` 为当前时间。

（5）若开启先审后发，管理员在 `GET /v1/admin/listings?status=PENDING` 中通过或驳回，驳回写入 `reject_reason`；商品被下单时状态转 LOCKED，禁止改价与下架，防止一物二卖。

**技术要点**　品相用五档枚举而非自由文本，因为它参与定价与过滤，自由文本无法聚合；以 VARCHAR 存英文枚举，库中看到 `LIKE_NEW` 比看到 `2` 更易排障。图片按 MD5 判重可拦住一张图批量发多本书；服务端压至长边一千二百像素使体积降一个数量级，前端持临时凭证直传对象存储，业务接口只收地址。定价参考是命中 `idx_textbook_status` 的聚合查询并加五分钟缓存，审核默认先发后审以保证开学季供给速度。

**关键表与接口**　表：`biz_listing`、`biz_listing_image`、`sys_textbook`、`biz_orders`（成交价来源）、`biz_favorite`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/listings` | 发布商品 |
| PUT | `/v1/listings/{id}` | 修改商品 |
| GET | `/v1/listings/{id}` | 商品详情 |
| POST | `/v1/listings/{id}/offline` | 下架 |
| POST | `/v1/uploads/images` | 图片上传 |
| GET | `/v1/listings/price-reference` | 定价参考，参数 textbookId |

### 5.4 模块四 检索、匹配与推荐

**功能描述**　解决买家如何找到想要的书。关键词检索按书名、作者、出版社、版次匹配并做相关度排序；按课程筛选后只看到该课程在售教材；排序支持相关度、价格升序、最新发布与距离由近到远；同课程教材聚合以课程为单位分组并展示在售数量与最低价；个性化推荐基于 ItemCF，冷启动按课程热度兜底。

**业务流程**

（1）用户输入关键词，前端三百毫秒防抖后请求 `GET /v1/listings/search`。

（2）服务端预处理：去空格、全角转半角、识别是否为纯数字 ISBN；是则按 `textbook_id` 精确匹配，否则进入模糊检索。

（3）检索在 `biz_listing.title` 与关联 `sys_textbook` 的 title、author、publisher 上执行，过滤 `status='ON_SALE'`、`deleted=0`，按选择排序并分页；结果页把同一教材的多条商品折叠成组，组头显示教材名、版次与在售数量。

（4）用户进详情或收藏时上报事件并写入 `biz_favorite`；`GET /v1/recommend/listings` 取最近浏览与收藏，查离线相似度结果，过滤已售、自己发布与已下架，不足时用课程热度补齐。

（5）离线任务每日凌晨以同一用户收藏或购买过两个商品为共现信号重算相似度，保留每个商品的前五十个邻居。

**技术要点**　Elasticsearch 功能最强，但引入额外进程与运维成本，对商品数不超过五万的单校系统属过度设计；MySQL 8 的 `FULLTEXT` 配 ngram 虽支持中文，二元切分噪声大且难与多表连接配合，故采用 ISBN 精确、标题前缀走 `idx_title`、LIKE 兜底的混合策略并在应用层加权。距离取宿舍楼到自提点的相对距离，因为校园范围通常在一千五百米内，经纬度计算对体验改善有限。推荐选 ItemCF 因商品数远小于用户数、相似度矩阵稳定且无需训练，相似度为 `sim(i,j) = |N(i) ∩ N(j)| / sqrt(|N(i)| × |N(j)|)`，共现低于二十时改用课程热度。

**关键表与接口**　表：`biz_listing`、`sys_textbook`、`sys_course`、`biz_favorite`、`biz_orders`、`biz_track_event`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/listings/search` | 关键词检索，参数 keyword、courseId、sort |
| GET | `/v1/courses/{courseId}/listings` | 同课程在售聚合 |
| GET | `/v1/recommend/listings` | 个性化推荐 |
| GET | `/v1/search/suggest` | 搜索联想词 |
| GET | `/v1/search/hot` | 热门课程与教材 |

### 5.5 模块五 订单与担保交易

**功能描述**　本模块是资金与状态的核心。订单号格式为 `TB` 加十四位时间加六位随机数；状态机取值为 PENDING_PAY、FROZEN、WAIT_VERIFY、VERIFIED、SETTLED，另有 REFUNDED、CLOSED 两个终态；资金流为三段式——支付后冻结、核销后确认、结算后打款，平台不设资金池；幂等下单以客户端 requestId 与 `sys_idempotent` 唯一键去重；超时未支付默认十五分钟自动关单；靠条件更新与行锁防止超卖。

**业务流程**

（1）买家点击立即购买，前端生成 UUID v4 作为 requestId 并在按钮上加锁防连点。

（2）`POST /v1/orders` 先向 `sys_idempotent` 插入 `(requestId, 'CREATE_ORDER')`；主键冲突说明已处理，直接读 `result` 中的订单号快照返回。

（3）校验商品为 ON_SALE、卖家非买家本人、自提点有效，执行 `UPDATE biz_listing SET status='LOCKED' WHERE id=? AND status='ON_SALE'`；受影响行数为零说明已被抢，事务回滚。

（4）写入 `biz_orders`，`status` 为 PENDING_PAY，`expire_at` 为当前时间加十五分钟，回填幂等表快照。

（5）`POST /v1/orders/{orderNo}/pay` 发起支付，回调经 `POST /v1/pay/notify` 处理，以 `trade_no` 为幂等键并以 `UPDATE ... WHERE order_no=? AND status='PENDING_PAY'` 推进为 FROZEN。

（6）卖家送达并点已送达转 WAIT_VERIFY；店员核销转 VERIFIED 并生成待结算单；每日结算任务扫描 VERIFIED 超过二十四小时的订单生成批次打款，转 SETTLED 并写 `settled_at`。

（7）超时任务每分钟扫描 `status='PENDING_PAY' AND expire_at < NOW()` 的订单，置 CLOSED 并写 `closed_at`，把仍为 LOCKED 的商品恢复为 ON_SALE；退款则置 REFUNDED，商品恢复在售，结算单置 FAILED。

**技术要点**　状态机把迁移规则显式建模：定义 `OrderStatus` 枚举与迁移表 `Map<OrderStatus, Set<OrderStatus>>`，所有变更必须经 `OrderStateMachine.transit(order, target)`，不合法即抛业务异常。防超卖靠条件更新 `WHERE id=? AND status='ON_SALE'`，命中行加排他锁，并发事务只有一个能改为 LOCKED；`listing_id` 只建普通索引，因为关单或退款后允许再次下单。幂等表以 `(request_id, scene)` 为复合主键，插入成功即抢到处理权，`result` 保存首次结果摘要供回放；关单与回调竞争时失败方读最新状态走补偿，已关单却收到支付成功则自动退款。

**关键表与接口**　表：`biz_orders`、`sys_idempotent`、`biz_listing`、`biz_settlement`、`biz_pickup_verify`、`msg_notice`。

### 5.6 模块六 自提点与核销履约

**功能描述**　完成线上交易到线下交付的最后一环。自提点管理维护名称、地址、营业时间、货位容量与负责店员；核销码为待核销订单生成带过期时间的动态码并由 HMAC 签名保护；店员扫码后由服务端验签、校验时效与订单状态；核销记录留存订单号、自提点、店员、方式、客户端地址与时间；核销成功后自动创建结算单。

**业务流程**

（1）管理员创建自提点并指定店员，写入 `biz_pickup_point`；买家下单时选择自提点，`biz_orders.point_id` 记录该选择。

（2）订单进入 FROZEN 或 WAIT_VERIFY 后，买家请求 `GET /v1/orders/{orderNo}/verify-code`。

（3）服务端取订单标识、随机数 nonce 与过期时间戳，拼接为 `orderId|nonce|expire`，用服务端密钥做 HMAC-SHA256 取前十六字节，与原文一起 Base64URL 编码成短码；前端展示三十秒倒计时并自动刷新。

（4）店员 `wx.scanCode` 扫码请求 `POST /v1/verify/scan`；服务端重算签名比对，校验未过期（允许正负六十秒偏差）、订单为 WAIT_VERIFY、自提点与店员所属一致。

（5）单事务内条件更新订单为 VERIFIED 并写 `verified_at`、插入 `biz_pickup_verify`、更新商品为 SOLD、插入待结算单；任一失败整体回滚，随后向双方发送站内消息。

**技术要点**　核销码是无状态的一次性凭证，目标是不可伪造、不可长期复用、可离线校验。选 HMAC 而非数据库随机码，因为无需每次展示写库，服务端只持密钥即可验证；过期时间编码进码值，使验签阶段就能拒绝过期码、省一次查库。密钥从环境变量读取且不少于三十二字节，截断十六字节对抗在线爆破足够，Base64URL 避免 `+`、`/`、`=` 在 URL 与二维码中的转义问题。防重放靠三十秒时效、核销只能从 WAIT_VERIFY 迁移、`biz_pickup_verify.order_id` 唯一键三层机制；连续失败超阈值时临时锁定店员账号。

**关键表与接口**　表：`biz_pickup_point`、`biz_pickup_verify`、`biz_orders`、`biz_settlement`、`msg_notice`。

| POST | `/v1/admin/pickup-points` | 新增自提点 |

### 5.7 模块七 信用评价与纠纷工单

**功能描述**　承担交易后的信任沉淀与争议处理。买卖双方在订单结算后七天内互评，支持一至五星、文字与图片、可选匿名，同一订单同一角色只能评一次；信用分初始一百分，成交加二分、好评加一分、超时扣五分、售假扣二十分、纠纷败诉扣十分，区间零至一百五十分，每次变动写 `biz_credit_log` 流水；纠纷工单就退款、假书、品相不符发起，由管理员受理并给出结论；违规处置依据结论下架商品、冻结账号或扣分。

**业务流程**

（1）订单转 SETTLED 后开放评价入口，`POST /v1/orders/{orderNo}/reviews` 校验订单归属与状态，插入 `biz_review`，`uk_order_role` 拦截重复评价。

（2）同事务内更新被评价人信用分：`SELECT ... FOR UPDATE` 锁定 `sys_user` 行，按规则计算并夹取到合法区间，更新 `credit_score`，插入流水并写 `score_after`。

（3）卖家评价走同一接口，`reviewer_role` 为 SELLER，唯一键保证互不冲突。

（4）买家 `POST /v1/tickets` 创建工单，类型取 REFUND、FAKE_BOOK、CONDITION、OTHER，`status` 为 PENDING；管理员受理置 PROCESSING，双方留言写入 `biz_ticket_message`。

（5）`POST /v1/admin/tickets/{id}/resolve` 填写说明并置 RESOLVED 或 REJECTED，写 `result`、`closed_at`；结论为卖家责任时联动退款、下架、扣分乃至冻结，操作写入 `sys_admin_log`。

**技术要点**　信用分的一致性靠行锁加流水：分数是聚合结果、流水是事实记录，只改分不写流水则事后无法解释来源，只写流水不改分则展示值失真，故两个写操作同一事务并先对用户行加排他锁。流水同时记 `change_val` 与 `score_after`，可校验不变式：任一条的 `score_after` 应等于上一条的 `score_after` 加本条 `change_val`。同一订单的成交加分利用 `ref_type` 与 `ref_id` 查重，该检查在并发下不严格，生产环境应在 `(user_id, reason, ref_type, ref_id)` 建唯一索引，本设计未建，是出于演示数据灵活性的简化。匿名只在展示层隐藏昵称与头像，库中仍保留 `reviewer_id` 供追溯。

**关键表与接口**　表：`biz_review`、`biz_credit_log`、`biz_ticket`、`biz_ticket_message`、`sys_user`、`sys_admin_log`。

| --- | --- | --- |
| POST | `/v1/orders/{orderNo}/reviews` | 提交评价 |
| GET | `/v1/users/{userId}/reviews` | 用户收到的评价 |
| GET | `/v1/credit/logs` | 我的信用流水 |

### 5.8 模块八 班级接龙与运营看板

**功能描述**　面向供给聚合与运营决策。团长以课程为单位发起班级接龙，设定目标册数、预期单价、截止时间与佣金比例并生成唯一邀请码；同学经邀请码登记册数与联系方式，同一接龙内每人仅一次；登记达标后可确认成团，状态由 OPEN 转 CLOSED 或 DONE；埋点采集浏览、详情、发布、下单、支付、核销行为；日统计汇总成交额、订单数、核销数、新上架数、新增用户与退款数，看板展示趋势与转化漏斗。

**业务流程**

（1）团长选课程并填写标题、目标册数、预期单价、截止时间与佣金比例，提交 `POST /v1/group-buys`，服务端生成六位邀请码写入 `biz_group_buy`，`status` 为 OPEN。

（2）同学经 `GET /v1/group-buys/{inviteCode}` 查看已登记册数、还差多少与截止时间，填写册数与联系方式请求 `POST /v1/group-buys/{inviteCode}/join`。

（3）服务端插入 `biz_group_buy_item`（`uk_group_user` 防重复），同时以 `UPDATE biz_group_buy SET current_count = current_count + ? WHERE id = ?` 原子累加。

（4）截止后定时任务把仍为 OPEN 的接龙置 CLOSED；`current_count` 达标时团长确认成团置 DONE，生成待匹配清单并支持导出。

（5）小程序批量上报 VIEW_LISTING、DETAIL、PUBLISH、CREATE_ORDER、PAY、VERIFY 事件至 `POST /v1/track/events`，附带会话标识与关联对象。

（6）每日凌晨一时聚合前一日数据写入 `stat_daily`：成交额取当日 SETTLED 订单金额之和，订单数取当日创建数，核销数取当日核销记录数，新上架数取当日发布数，新增用户取当日注册数，退款数取当日转 REFUNDED 的订单数。

（7）看板读 `GET /v1/admin/stats/overview` 取当日与近三十日汇总；漏斗读 `GET /v1/admin/stats/funnel` 按事件分组统计去重会话数，计算浏览到详情、详情到下单、下单到支付、支付到核销的转化率。

**技术要点**　接龙计数的并发安全是本模块重点：登记含插入明细与更新计数两步，先查后改会读到相同旧值导致计数偏小，故把加法交给数据库由 InnoDB 行锁串行化，另设每日校准任务按明细重算修正主表以防漂移。邀请码六位、三十二字符集，去掉 0 与 O、1 与 I 因为主要靠口头传播与手输，生成后查唯一键、冲突重试最多五次。埋点异步、批量且可丢弃，不允许阻塞主链路。日统计表用空间换时间：看板若每次从订单表聚合要扫描数十万行并分组，预聚合把计算前移到凌晨低峰，查询退化为读三十行；漏斗按 `session_id` 去重而非 `user_id`，因为未登录用户也产生浏览。

**关键表与接口**　表：`biz_group_buy`、`biz_group_buy_item`、`biz_track_event`、`stat_daily`、`msg_notice`。

### 6.2 为何不采用 NestJS

其一，事务与并发控制：订单模块依赖行锁、条件更新与隔离级别，Spring 的 `@Transactional` 与 MyBatis 组合更直接，Node 侧 ORM 在锁语义上表达力较弱，易出现看似加了事务实际未生效。其二，复杂聚合查询：定价参考、看板与漏斗都需手写聚合 SQL，MyBatis 允许把 SQL 写在 XML 中直接调试。其三，学校课程体系以 Java 为主，答辩教师更熟悉 Spring 技术栈。其四，Spring Boot 打成单个可执行 JAR，配合 Docker 镜像部署简单。

### 6.3 为何前端不选 Taro

项目只发布微信一端，多端编译的能力用不上，却要承担额外构建链路与版本兼容成本。Taro 的跨端抽象在调用 `wx.login`、`wx.scanCode` 等平台专有能力时会产生封装层，出问题需同时排查业务代码、适配层与基础库，排障路径变长。原生框架学习成本低、页面体积小；管理后台是独立 Web 应用，与小程序不共享代码。

### 6.4 可行性

技术可行性：所选技术均为成熟方案，微信登录、支付、扫码接口文档完整，单体架构、模块边界清晰，单人可在十二周内完成主要功能。经济可行性：一台两核四G云服务器即可支撑单校试运行，月度成本在百元量级，平台不设资金池、无垫资压力。操作可行性：用户侧零安装，发布控制在三步以内，核销只需扫码一次。进度可行性：模块彼此解耦，认证、知识库、商品、检索可并行推进，订单与核销集中攻关。

## 七、技术难点与解决方案

### 7.1 教材版本歧义

难在：教材书名是自然语言，"高等数学上册"可能指同济第六版、第七版或其他出版社版本，文本相似度极高但业务上不可互换。一旦错版，习题编号对不上，交易必然退货；更麻烦的是错误在成交当下不会暴露，往往等上课才发现，此时书已核销、款已结算。

解法是三重结构化约束：主数据层以 ISBN 为唯一键，一书一版一条记录，书名与版次分列、版次必填；关系层让映射携带教师与学期，形成"课程 + 教师 + 学期 → 教材"的三元组；流程层要求发布必须从教材库选择，选课后带出指定教材，手中是旧版必须显式切换到参考教材，这个动作本身即是提醒。

### 7.2 担保交易的资金一致性与幂等

难在：支付回调可能重复投递、乱序到达，用户可能连点下单，多个买家可能同时抢同一本书，而资金状态与订单状态必须严格同步。任何一步失败都会产生钱货不一致：钱扣了单没生成、单生成了书被抢走、书核销了钱没结算；这类问题在演示环境不易复现，却会在试运行第一天集中爆发。

解法是三层控制：状态机层所有变更经白名单校验并使用条件更新，把并发收敛到数据库行锁；幂等层下单以 requestId 为键、回调以第三方流水号为键，写入 `sys_idempotent` 复合主键，插入成功才处理，失败回放首次结果；补偿层在关单与回调竞争同一行时让失败方读最新状态，若已关单但收到支付成功则自动退款并记异常，保证最终一致。

### 7.3 核销码的防伪与防重放

难在：核销码展示在用户手机屏幕上，可被截图转发；线下网络可能不稳定，无法每次实时查库；重复核销会导致重复结算，直接造成资金损失；同时码值还要足够短，能被普通摄像头在光线不佳的自提点稳定识别。

解法是签名、时效、状态机与唯一键的组合：码值由订单标识、随机数与过期时间拼接后做 HMAC-SHA256，截断十六字节并 Base64URL 编码，服务端只验签不存码，天然防篡改；有效期三十秒并允许六十秒偏差，截图转发后大概率过期；防重放不依赖 nonce 水位，而依赖订单状态的条件更新与核销记录唯一键，两层都在库层生效；核销时额外校验店员所属自提点与订单一致，防止跨点核销。

### 7.4 冷启动无供给

难在：上线初期既无商品也无行为数据。没有商品，买家来了就走；没有行为，ItemCF 算不出相似度；校园场景还有强季节性，开学两周内需求集中爆发，而供给需要时间积累。这是先有鸡还是先有蛋的问题，纯技术手段无法解决。

解法分供给端与算法端：供给端用班级接龙把分散需求聚合成确定的采购量，团长发起、同学登记、成团后统一组织货源或与书店谈批量折扣，平台按成交额给佣金，把获客成本转移给有组织能力的节点，使平台在零库存下获得确定的供给信号；算法端分级兜底，行为不足时按课程热度排序，热度由近七天浏览、收藏与成交量加权，商品共现用户数超过二十才启用协同过滤，两者混合排序且协同过滤权重随数据积累提高。
